Monitoring fonctionnel des apps VPS

Spécification produit et technique pour observer, alerter et diagnostiquer les apps déployées sur Hetzner — avec stylot comme premier client de production.

Demande — « Topo exhaustif, specs/PRD, d'après l'audit, pour mettre en place le monitoring fonctionnel d'une app en VPS. Je vais bientôt déployer stylot en production : il faut que je puisse le monitorer correctement. »

L'audit a montré que la moitié du travail est déjà faite côté émission : Vector est installé sur chaque VPS, le pipeline de relabel VictoriaMetrics est écrit et testé, postgres-exporter existe pour Supabase. Mais aucun récepteur n'est déployé : NN_VL_URL n'est pas défini, donc Vector dort sur toute la flotte, et rien ne collecte de métriques machine. Ce PRD spécifie la chaîne complète — VictoriaLogs + VictoriaMetrics + vmalert + Alertmanager sur nn-internals, node_exporter + cAdvisor dans la golden image, découverte par tag Tailscale — en 6 phases (~9 j). Le chemin critique pour mettre stylot en prod monitoré s'arrête à la phase P3 : ~5,5 jours.

01Objectifs & non-objectifs

« Monitorer correctement stylot » se décompose en quatre capacités vérifiables, chacune avec un délai de détection cible.

✅ Objectifs

  • Savoir que ça tourne — VPS up, conteneurs up, healthchecks verts, sondes HTTP externes. Détection d'une panne < 5 min.
  • Savoir comment ça tourne — CPU, mémoire, disque, réseau par VPS ; CPU/mémoire/restarts par conteneur ; taux d'erreurs et latence HTTP par domaine.
  • Être prévenu sans regarder — alertes par email, dédupliquées, avec un dead man's switch externe qui couvre la panne du monitoring lui-même.
  • Diagnostiquer après coup — logs centralisés requêtables (app + postgres + Caddy + système), 30 j de rétention, corrélables aux métriques par projet/VPS.
  • Zéro action par app — une fois la plateforme posée, un nouveau projet (stylot, le suivant…) est monitoré automatiquement dès son provisioning, sans rien dans son repo.

🚫 Non-objectifs (v1)

  • Tracing distribué (OpenTelemetry) — un seul service par app aujourd'hui, pas de chaîne à tracer.
  • Grafana — l'app Astro monitoring reste le front ; vmui sert l'exploration ad-hoc. Réévalué si les dashboards custom coûtent trop cher (P5).
  • Métriques applicatives custom (compteurs métier dans le code stylot) — optionnel post-v1, le socle les acceptera sans refonte.
  • Haute dispo du monitoring — nn-internals reste un SPOF assumé, couvert par le dead man's switch externe.
  • Monitoring des sites statiques Cloudflare Pages — déjà couvert par les stats Cloudflare dans l'app monitoring.
Principe directeur Push pour les logs (Vector pousse vers VictoriaLogs), pull pour les métriques (vmagent scrape via le tailnet). Tout transite par Tailscale : aucun port public nouveau, aucune auth applicative à gérer — la membership tailnet est la frontière de confiance, comme pour l'app monitoring actuelle.

02État des lieux — ce que l'audit a établi

Trois briques émettrices existent, écrites et testées ; les trois briques réceptrices n'existent nulle part. Le système est un émetteur sans antenne.

✅ Déjà posé (code livré)

  • Vector sur chaque VPS — installé par la golden image (golden-image.ts:94), unit systemd, config générée à la convergence : sources docker_logs + journald, enrichissement nn_client_id/nn_project, sink VictoriaLogs /insert/jsonline?_stream_fields=nn_project,nn_client_id (vector-toml.ts:35-70).
  • Hot-update sans rebuild — converge.ts:35-55 pousse vector.toml + vector.env par SFTP et redémarre Vector dès que NN_VL_URL apparaît. Activer les logs sur la flotte = définir 2 variables et re-provisionner.
  • Pipeline de relabel complet — client-vps-relabel.ts : filtre tag:client-vps, mapping __meta_nextnode_* → whitelist fermée de 7 labels (client_id, project, environment, vps_name, container_name, region, db_role), labelkeep final. Budget de cardinalité déjà conçu, rendu YAML prêt à splicer.
  • postgres-exporter en production — sidecar Supabase v0.18.0, bind ${TAILSCALE_IP}:9187, rôle pg_monitor, requêtes custom, rotation de mot de passe par commande dédiée. C'est le pattern de référence pour tout exporter conteneurisé.
  • Multi-service par projet opérationnel — [deploy.services.*] build/upstream, .env.<name> par service, depends_on, healthcheck /healthz obligatoire pour les services build.
  • App monitoring (control plane) — Astro sur nn-internals (cx33, internal=true, tailnet only), adapters Hetzner/Cloudflare/Tailscale-OAuth déjà écrits, placeholders UI explicites pour « Live host metrics », « Live container logs », « Caddy access logs ».

❌ Absent (à construire)

  • VictoriaLogs — déployé nulle part. NN_VL_URL non défini ⇒ la convergence saute la config Vector (converge.ts:54) ⇒ aucun log n'est collecté aujourd'hui, sur aucun VPS.
  • VictoriaMetrics / vmagent — aucun stockage ni scrape de métriques. Le relabel n'a aucun consommateur.
  • node_exporter / cAdvisor — pas dans la golden image : zéro métrique machine ou conteneur.
  • Tag tag:client-vps jamais appliqué — cloud-init.ts:89 fait tailscale up --authkey --hostname sans --advertise-tags. La découverte par tag est une convention documentée, pas un fait.
  • vmalert / Alertmanager / canaux — aucune règle, aucun routage, aucune notification. Panne silencieuse garantie.
  • Caddy access logs — non configurés : aucune visibilité HTTP (statuts, latence) sur les vhosts.
  • Couche SD — les labels __meta_nextnode_* attendus par le relabel ne sont émis par rien.
  • postgres-exporter pour Postgres embedded — réservé à Supabase ; le sidecar postgres:18 n'est pas instrumenté.
Fait structurant L'app monitoring est volontairement un control plane UI sans agent de fond — leçon de la branche feat/monitoring-package abandonnée (pipeline multi-tenant à moitié fini, complexité explosive). Le backend d'observabilité doit donc vivre dans des conteneurs dédiés à côté de l'app, pas dans l'app. Ce PRD respecte cette frontière : l'app ne fait que des GET de lecture (requêtes PromQL/LogsQL, endpoint SD stateless).

03Architecture cible

Une stack d'observabilité co-localisée avec l'app monitoring sur nn-internals, alimentée en push (logs) et en pull (métriques) à travers le tailnet. Les notifications sortent par Resend ; un heartbeat externe surveille le surveillant.

Cinq décisions de design structurent cette cible :

  • La stack vit dans le projet monitoring existant, déployée par le pipeline standard sur nn-internals. Pas de VPS supplémentaire, pas de déploiement manuel : la stack d'observabilité est elle-même une app NextNode, avec les garanties du pipeline (état R2, convergence idempotente, secrets scopés).
  • Suite VictoriaMetrics (VictoriaLogs, VictoriaMetrics, vmagent, vmalert) plutôt que Prometheus + Loki : le code existant la cible déjà (sink /insert/jsonline = API VictoriaLogs, relabel commenté « VictoriaMetrics »), un seul éditeur, binaires légers adaptés à un cx33 (4 vCPU / 8 Go), vmui inclus pour l'exploration ad-hoc.
  • Exporters au niveau hôte via la golden image (node_exporter binaire, cAdvisor conteneur systemd) — ils observent l'hôte, ils appartiennent à l'image, pas aux projets. Aucun nextnode.toml client n'est modifié.
  • Découverte par tag Tailscale + état R2 — vmagent interroge un endpoint http_sd stateless servi par l'app Astro, qui joint l'API Tailscale (devices tag:client-vps) et l'état R2 (hetzner/<vps>.json : projets, environnements) pour émettre les cibles avec les labels __meta_nextnode_* que le relabel existant attend.
  • Alertmanager unique, email d'abord — routage Resend SMTP (brique déjà dans l'écosystème via email-manager), heartbeat healthchecks.io en dead man's switch. Slack/ntfy : ajout trivial plus tard, décision ouverte (§13).

04Les cinq signaux — quoi collecter, comment, avec quels labels

Chaque type de signal a sa source, son transport et son budget de cardinalité. La whitelist de 7 labels de client-vps-relabel.ts est le contrat transverse : toute série qui sort du lot est supprimée au scrape.

Source — Vector sur chaque VPS : docker_logs (toutes les apps, postgres, sidecars) + journald (Caddy, sshd, kernel, et les access logs Caddy à partir de P4). Transport — push HTTPS vers logs.monitoring.nextnode.fr (vhost Caddy tailnet devant VictoriaLogs). Déjà écrit : il ne manque que le récepteur et les 2 variables d'environnement.

  • Stream fields : nn_project, nn_client_id — déjà dans le sink (vector-toml.ts:35). Les requêtes par projet sont indexées nativement.
  • Rétention : 30 j (-retentionPeriod=30d), volume estimé < 1 Go/j pour la flotte actuelle.
  • Requêtage : LogsQL — par projet ({nn_project="stylot"}), par conteneur (champ container_name émis par docker_logs), stats (| stats by (...)) pour les analyses HTTP P4.
  • Garde-fou : alerte VectorSilent (P3) — un VPS qui n'émet plus de logs pendant 15 min est signalé, ce qui couvre la panne Vector elle-même.

Source — node_exporter (binaire statique pinné, unit systemd, golden image P2), collecteurs par défaut : CPU, mémoire, disque, filesystem, réseau, load, pression. Transport — scrape vmagent 15 s via tailnet, port 9100 ouvert UFW sur tailscale0 uniquement.

  • Labels (via SD + relabel existant) : vps_name, client_id, project, environment, region. Une série machine porte le VPS, pas un conteneur.
  • Cardinalité : ~800–1200 séries par VPS — négligeable.
  • Cas multi-tenant : un VPS hébergeant plusieurs projets émet ses métriques machine une seule fois ; le label project reflète le projet « propriétaire » du VPS dans l'état R2, les vues par projet croisent avec les métriques conteneurs.
  • nn-internals n'est pas taggué client-vps (le relabel l'exclut volontairement) : il est scrappé par un job statique self séparé — le monitoring se surveille aussi.

Source — cAdvisor (conteneur Docker lancé par une unit systemd de la golden image, P2), publié ${TS_IP}:9101:8080 pour éviter la collision avec la plage de ports apps [8080, 8200). Transport — scrape vmagent via tailnet ; le mapping de port Docker contourne UFW par iptables, exactement comme postgres-exporter aujourd'hui.

  • Métriques clés : CPU/mémoire par conteneur, container_last_seen (détection de conteneur disparu), restarts, OOM kills, I/O.
  • Cardinalité — le vrai risque : cAdvisor émet par défaut des dizaines de labels (container_label_*, ids longs). Mitigation : metric_relabel_configs générés en TS — ne garder que name → container_name + la whitelist, drop du reste. Budget cible < 2 000 séries/VPS.
  • Le nom de conteneur compose (<projet>-<env>-<service>…) permet de rattacher chaque conteneur à son projet dans les dashboards P5.

Deux angles complémentaires (P4) — la vérité interne (access logs Caddy) et la vérité externe (sondes blackbox).

  • Access logs Caddy : activer le log JSON par vhost dans le générateur de config Caddy (aujourd'hui : zéro access log). Caddy tourne sous systemd → ses logs partent dans journald → Vector les expédie déjà : activer le log = la chaîne complète fonctionne sans plomberie nouvelle. On en tire statuts, latence (champ duration), volumes par domaine — en LogsQL.
  • blackbox_exporter sur nn-internals : probe HTTPS de chaque domaine public (stylot prod + dev) depuis l'extérieur du VPS cible — vue « est-ce que ça répond pour un visiteur », TLS handshake, chaîne de certificat, probe_ssl_earliest_cert_expiry pour l'expiration.
  • Cibles des probes : dérivées du même endpoint SD (les domaines sont dans l'état/config des projets) — zéro liste à maintenir.
  • Limite assumée : blackbox probe depuis Hetzner/nbg1, pas depuis un point mondial. Le dead man's switch healthchecks.io ajoute le seul regard vraiment externe ; un UptimeRobot gratuit sur stylot peut compléter (question ouverte §13).

Source — postgres-exporter, déjà en production pour Supabase. P6 le généralise au sidecar Postgres embedded (postgres:18) en réutilisant postgres-exporter.ts tel quel : même image, même bind ${TAILSCALE_IP}:9187, même mécanique de mot de passe (secret généré idempotent + commande de rotation existante).

  • Métriques : pg_up, connexions vs max_connections, taille des bases, transactions, locks, requêtes lentes (custom queries déjà écrites pour Supabase).
  • Label réservé db_role : le slot existe dans la whitelist — le câbler ici si le besoin par-rôle revient, sinon le laisser dormant (décision §13).
  • Fraîcheur des backups : le conteneur postgres-backup (GFS vers R2) pousse à la fin de chaque run un sample nn_backup_last_success_timestamp_seconds vers VictoriaMetrics (/api/v1/import/prometheus, une ligne de curl dans le script). Alerte si > 26 h. C'est la seule métrique « push » du système, et elle ferme le risque « backups silencieusement cassés » relevé par l'audit.

05Découverte des cibles — brancher le relabel qui attend

Le pipeline de relabel est écrit, testé, et exige des labels __meta_tailscale_* / __meta_nextnode_* qu'aucune couche n'émet. La spec ci-dessous comble exactement ce trou, sans inventer de nouveau format.

Spécification de l'endpoint SD :

  • Où — route API de l'app monitoring (src/pages/api/sd/targets.ts). C'est un GET pur : lecture API Tailscale + lecture R2, jointure par hostname, cache LRU 60 s (le wrapper cachified est déjà une dépendance). Pas d'agent de fond, pas d'état : la leçon du reset est respectée.
  • Pourquoi pas un conteneur SD dédié — l'app a déjà l'adapter OAuth Tailscale (lib/adapters/tailscale/oauth.ts, écrit et inutilisé) et le secret TS_OAUTH_SECRET dans son nextnode.toml. Il manque seulement un adapter R2-state (lecture seule du bucket nextnode-state) : +2 secrets (R2_ACCESS_KEY_ID, R2_SECRET_ACCESS_KEY) dans la liste du service app.
  • Sortie — format http_sd standard : une entrée par couple (VPS taggué client-vps) × (port exporter 9100, 9101, 9187 si présent), avec __meta_tailscale_device_tags, __meta_tailscale_device_hostname, __meta_nextnode_client_id, __meta_nextnode_project, __meta_nextnode_environment — les noms exacts attendus par SOURCE_BY_LABEL.
  • Prérequis tailnet (P2) — (a) cloud-init.ts:89 ajoute --advertise-tags=tag:client-vps au tailscale up ; (b) ACL Tailscale : tagOwners pour tag:client-vps + tag:monitoring, et un grant tag:monitoring → tag:client-vps:9100,9101,9187. L'authkey éphémère doit être minté avec le tag (modification du mint OAuth existant).
  • vmagent — deux jobs : client-vps (http_sd + relabel rendu par renderClientVpsRelabelYaml() — premier consommateur réel du module) et self (cibles statiques localhost : node_exporter et cAdvisor de nn-internals, VictoriaLogs/VM eux-mêmes, labels project="monitoring").

P1 — Backing service observability

Le point de design central : les conteneurs VictoriaMetrics/vmalert/Alertmanager ont besoin de volumes persistants, de flags de commande et de fichiers de config — trois choses que [deploy.services.*] ne sait pas exprimer (volumes sur le service primaire uniquement, pas de command, pas de fichiers). Deux options :

A — Backing service [services.observability] (recommandé)

  • Même mécanique que Supabase : un flag TOML injecte une stack de sidecars complète dans le compose généré, configs rendues en TS (testées unitairement), volumes et binds gérés par le générateur.
  • Cohérent avec le ban YAML-logic du repo : les règles vmalert, le scrape config et alertmanager.yml deviennent des modules domain/monitoring/* purs — comme client-vps-relabel.ts l'anticipait (« consumers splice the fragment at deploy time »).
  • Complétude compile-time du registre SERVICE_DEFINITIONS : teardown, état, validation gratuits.
  • Coût : ~1,5 j de dev infra (le moule Supabase existe), mais chaque évolution de règle d'alerte = un commit TS testé.
vs

B — Étendre le schéma générique (command, volumes, files par service)

  • Plus flexible pour des futurs services upstream quelconques.
  • Mais les configs (rules YAML, alertmanager.yml) vivraient en fichiers bruts dans le repo monitoring — précisément le YAML non testé que le repo bannit.
  • Trois extensions de schéma + validation + compose pour un seul cas d'usage réel aujourd'hui.
P1 — contenu détaillé de la stack et du nextnode.toml

Conteneurs injectés par le générateur (images pinnées par digest, volumes nommés, réseau compose standard) :

  • victorialogs — volume vl-data, exposé via vhost Caddy logs_vhost. C'est l'URL que prend NN_VL_URL.
  • victoriametrics — volume vm-data, vhost metrics_vhost pour vmui ; API /api/v1/* consommée par l'app via le réseau compose.
  • vmagent (P2), vmalert (P3), alertmanager (P3), blackbox (P4) — configs bind-mountées, générées en TS et poussées par SFTP au deploy comme caddy/config.json aujourd'hui ; volume am-data pour les silences.

Mise en service des logs, dans l'ordre : déployer P1 → définir la variable d'org NN_VL_URL=https://logs.monitoring.nextnode.fr + NN_CLIENT_ID=nextnode → relancer provision sur chaque projet VPS (la convergence écrit vector.toml/vector.env et redémarre Vector — chemin hot-update prévu par converge.ts:36). Vérification : {nn_project="monitoring"} renvoie des lignes dans vmui-logs.

P2 — Golden image, tag et SD

  • node_exporter — binaire statique pinné téléchargé dans l'image, unit node_exporter.service (--web.listen-address=:9100), enabled au build. Exposition contrôlée par double couche : le firewall Hetzner Cloud n'ouvre que 80/443/22, et UFW ajoute allow in on tailscale0 to any port 9100 proto tcp (cloud-init projet, cloud-init.ts).
  • cAdvisor — unit cadvisor.service de type docker run avec EnvironmentFile=/etc/monitoring/env et publication ${TS_IP}:9101:8080. L'IP tailnet n'existe pas au build de l'image : l'unit est installée disabled, la convergence écrit /etc/monitoring/env puis systemctl enable --now cadvisor — pattern identique à vector.env.
  • Tag — tailscale up … --advertise-tags=tag:client-vps (cloud-init projet) ; le mint d'authkey OAuth demande le tag ; ACL : tagOwners + grant tag:monitoring → tag:client-vps:9100,9101,9187. nn-internals reçoit tag:monitoring.
  • Effet de bord assumé — le cloud-init change ⇒ fingerprint bump ⇒ le workflow build-golden-image.yml reconstruit le snapshot (déclencheur sur ces paths déjà en place). Les VPS existants ne sont pas migrés automatiquement : recréer nn-internals (teardown-vps + provision, ~20 min d'indispo du monitoring, couverte par le DMS dès P3) ; tout VPS client actif devra être recréé ou migré à la main — à inventorier en P0.
  • Endpoint SD + vmagent — spec §5 ; le scrape config est généré en TS et splice renderClientVpsRelabelYaml() + les metric_relabel_configs cAdvisor (anti-cardinalité).

P3 — Alerting

P3 — routage Alertmanager, dead man's switch, extraits de règles

Le dead man's switch inverse la charge de la preuve : une règle Watchdog (expression vector(1)) fire en permanence, Alertmanager la pousse vers healthchecks.io toutes les ~4 min ; si nn-internals, vmalert ou Alertmanager meurt, le ping cesse et healthchecks.io envoie l'email depuis l'extérieur. C'est la réponse au SPOF assumé.

Validation P3 : chaque règle du catalogue (§7) est testée par injection réelle — docker stop, remplissage de disque, coupure Tailscale — avant d'être déclarée active. Le groupe type: vlogs requiert un spike de compatibilité vmalert ↔ VictoriaLogs en début de phase (risque §11).

P4 — HTTP & uptime

  • Générateur Caddy : ajouter le bloc log JSON par serveur (sortie stdout → journald → Vector → VictoriaLogs, chaîne déjà active). Champs exploités : statut, host, durée, taille. Aucune rotation à gérer.
  • blackbox_exporter : module http_2xx ; cibles = domaines publics issus du SD ; règles ProbeFailed, ProbeSlow, CertExpirySoon (sur probe_ssl_earliest_cert_expiry — filet sous l'auto-renouvellement Caddy).
  • Règles LogsQL HTTP : taux de 5xx par domaine, p95 de latence — sur les access logs Caddy.

P5 — Dashboards (app monitoring)

  • Les trois placeholders de VpsObservabilityPlaceholders.astro deviennent réels : host metrics (PromQL node_* par vps_name), container logs (LogsQL par nn_project + container_name), Caddy analytics (LogsQL stats par host/statut).
  • Le stub 501 GET /api/vps/[slug]/metrics s'implémente en proxy fin vers http://victoriametrics:8428/api/v1/query_range (réseau compose, pas de SSH probe — le plan initial « SSH + docker logs » est obsolète et supprimé).
  • Vue projet (/projects/stylot) : santé des conteneurs, CPU/mémoire, erreurs HTTP, liens vmui pré-remplis pour le drill-down.
  • Hors chemin critique stylot : vmui + les emails d'alerte suffisent à opérer dès P3.

P6 — Postgres embedded & backups

  • Généraliser l'injection du sidecar postgres-exporter au mode [services.postgres] embedded (le générateur Supabase se réutilise quasi tel quel : mêmes image, bind, secret généré, rotation).
  • Script postgres-backup : curl final vers /api/v1/import/prometheus avec nn_backup_last_success_timestamp_seconds{project=…}.
  • Règles : PgDown, PgConnectionsHigh, BackupStale (> 26 h).

08Exigences non fonctionnelles

Le système d'observabilité obéit aux mêmes contraintes que le reste de l'infra : tailnet-only, config générée et testée, coût marginal nul.

  • Sécurité réseau — aucun port public nouveau : exporters bindés tailnet (UFW tailscale0 pour node_exporter, publication Docker ${TS_IP} pour cAdvisor/postgres-exporter), vhosts VictoriaLogs/vmui résolus en IP tailnet (internal=true du projet monitoring), notifications en sortie uniquement. Vérif d'acceptation : scan externe = 80/443/22 seulement, identique à aujourd'hui.
  • Secrets — RESEND_API_KEY et HEALTHCHECKS_PING_URL entrent par le pool [deploy].secrets → provenance tracée, jamais broadcast. Le password postgres-exporter reste sur le mécanisme généré + rotation existant.
  • Cardinalité — whitelist 7 labels inchangée (contrat client-vps-relabel.ts) ; metric_relabel_configs cAdvisor obligatoires ; budget ~3 000 séries/VPS, alerte interne si VictoriaMetrics dépasse 100 k séries actives.
  • Rétention & volumétrie — métriques 12 mois (~< 5 Go/an à 5 VPS), logs 30 j (< 30 Go) : le disque 80 Go de nn-internals suffit, marge surveillée par DiskUsageHigh sur le job self.
  • Empreinte mémoire — VL + VM + vmagent + vmalert + AM + blackbox ≈ 1,5–2,5 Go ; l'app Astro < 300 Mo ; cx33 (8 Go) tient avec marge. Limites mémoire posées dans le compose généré pour borner un emballement.
  • Fraîcheur — scrape 15 s, évaluation des règles 30 s, logs visibles < 30 s après émission ; pire cas notification ≈ for + group_wait + SMTP ≈ condition + 1 min.
  • Fiabilité du pipeline — buffer disque Vector activé (aujourd'hui défaut mémoire : un VL indisponible = logs perdus silencieusement — quick win de l'audit intégré à P1) ; vmagent bufferise nativement vers VM.
  • Coût — 0 € logiciel (stack open source), 0 VPS ajouté, healthchecks.io plan gratuit. Seul coût : ~9 j de dev.

09Intégration stylot — ce que ça demande, ce qui est automatique

Par construction, stylot n'a presque rien à faire : le monitoring est une propriété de la plateforme, pas du projet. Trois conditions seulement, dont une d'ordonnancement.

  • → Provisionner le VPS stylot après P2 — il naît de la nouvelle golden image avec node_exporter/cAdvisor/tag. Un VPS créé avant devrait être recréé (pas de migration automatique d'image, fait confirmé par l'audit).
  • → Soigner /healthz — déjà obligatoire pour les services build (healthcheck compose 10 s/3 s/6 retries + gate deploy 60 s). Pour un monitoring utile, l'endpoint doit vérifier la dépendance critique (ping DB) et pas seulement « process up ».
  • → Si Postgres embedded : attendre P6 pour les métriques DB et la fraîcheur des backups (sinon Supabase : postgres-exporter déjà actif).

Tout le reste est automatique dès le provisioning : logs (Vector configuré à la convergence, stream nn_project="stylot"), métriques machine et conteneurs (tag → SD → scrape, labels project/environment), probes HTTP des domaines prod et dev (P4), couverture par les 18 règles du catalogue sans déclaration. Optionnel post-v1 : un endpoint /metrics applicatif (latence par route, métriques métier) — le job SD pourra l'ajouter sans refonte, décision à prendre quand le besoin existera.

10Risques & mitigations

Compatibilité vmalert ↔ VictoriaLogs moyen
Les règles LogsQL (type: vlogs — VectorSilent, 5xx, p95) dépendent de versions récentes des deux composants.
Spike de 2 h en ouverture de P3 sur les versions pinnées ; fallback : ces 4 règles passent en métriques dérivées (vmagent scrape l'API stats de VL) sans changer le catalogue.
Explosion de cardinalité cAdvisor moyen
Labels par défaut très verbeux ; un VPS multi-tenant chargé peut décupler les séries et saturer la RAM de VM.
metric_relabel_configs stricts dès P2 (whitelist de métriques + labels), alerte de budget de séries, limites mémoire compose.
Recréation de nn-internals moyen
P2 impose de recréer le VPS du monitoring : fenêtre sans collecte ni dashboards (~20–30 min), données VL/VM locales perdues si volumes non préservés.
Recréer avant la mise en prod de stylot (aucune donnée critique encore) ; ordonner P2 avant P3 pour que le DMS couvre les fenêtres suivantes ; à terme, volume Hetzner détachable (amélioration future, hors v1).
SPOF assumé du monitoring haut
Tout vit sur nn-internals : sa panne rend la flotte aveugle — le scénario qu'on cherche précisément à détecter.
Dead man's switch externe (healthchecks.io) : silence du heartbeat = email sous ~10 min, quoi qu'il arrive au tailnet. C'est le seul composant hors infrastructure propre, et c'est voulu.
Fatigue d'alerte moyen
18 règles sur une petite flotte : des seuils mal calibrés transforment l'email en bruit qu'on n'ouvre plus.
Groupement + repeat_interval: 4h, sévérités strictes (critical = action immédiate), revue des seuils après 2 semaines de prod stylot (critère d'acceptation §12).
Dépendances externes du SD faible
L'endpoint SD dépend de l'API Tailscale et de R2 ; une indispo fige la liste des cibles.
Cache 60 s + dernier snapshot servi en cas d'erreur amont ; vmagent garde ses cibles précédentes si le SD répond 5xx (comportement natif http_sd).

11Critères d'acceptation — « stylot est monitoré »

Huit scénarios de validation, tous testés par injection réelle de panne sur l'environnement dev de stylot avant la mise en prod.

  • 1 docker stop du conteneur stylot → email ContainerGone en moins de 5 min ; logs du conteneur lisibles dans VictoriaLogs au moment de l'incident.
  • 2 Remplissage artificiel du disque à 90 % → DiskUsageHigh en moins de 35 min, prédiction 24 h visible.
  • 3 Endpoint forcé en 500 pendant 6 min → Http5xxRateHigh (access logs Caddy), avec le domaine fautif dans l'email.
  • 4 tailscale down sur le VPS stylot → VpsDown + VectorSilent ; retour à la normale auto-résolu.
  • 5 Arrêt de nn-internals → email healthchecks.io (canal externe) en moins de 15 min.
  • 6 Dashboard /vps/<stylot> et /projects/stylot : CPU/mémoire/disque/conteneurs réels (placeholders supprimés), logs requêtables avec moins de 30 s de latence d'ingestion.
  • 7 Scan de ports externe du VPS stylot : 80/443/22 uniquement — le monitoring n'a rien exposé.
  • 8 Redeploy complet de stylot → aucune action monitoring nécessaire, les cibles SD suivent toutes seules ; après 2 semaines de prod : zéro alerte « bruit » non actionnable, sinon recalibrage des seuils.
