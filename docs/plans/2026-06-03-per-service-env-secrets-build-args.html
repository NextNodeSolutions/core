Secrets & build args par service :
le dev déclare, l'infra fait le reste

Chaque service ne reçoit que ce qu'il déclare. Fin du broadcast de DATABASE_URL vers le front. Build args uniformes (N variables, aucune privilégiée), valeurs dans GitHub, jamais dans le toml.

Objectif validé Le dev n'a quasi rien à faire : juste déclarer, par service, quels secrets (runtime) et quels build args il utilise. L'infra pull depuis GitHub, résout, projette par service. Least privilege par construction.

01 · Résumé & le finding confirmé

Finding (vérifié dans le code) : buildServiceSecretEnv (domain/hetzner/service-env.ts:71-89) broadcaste tout secret « non réclamé » à TOUS les services. Or DATABASE_URL (produit par le sidecar postgres) n'est réclamé par personne par son nom → il atterrit dans .env.front aujourd'hui. La fuite est réelle, masquée seulement parce que monitoring est mono-service. Le multi-service vient d'arriver → ça va mordre.

La couture exacte (3 fichiers)

Le problème : au point de projection, le map de secrets est opaque (merge dans resolve-deploy-context.ts:73-80 via mergeServiceEnvs — aucune provenance). Il faut threader « quelle backing-service a produit quelle clé ».

@@ signature @@ export function buildServiceSecretEnv( services: Readonly<Record<string, UserServiceConfig>>, secrets: Readonly<Record<string, string>>, + origins: Readonly<Record<string, string>>, // secretKey → backing service name ): Record<string, Record<string, string>> { - const claimed = new Set(services.flatMap(s => s.secrets)) - const broadcast = pick(secrets, key => !claimed.has(key)) // ← fuite for (const [name, service] of Object.entries(services)) { - byService[name] = { ...broadcast, ...declared(service) } + const backing = pick(secrets, key => + service.needs.includes(origins[key])) // projeté par needs, pas broadcast + byService[name] = { ...backing, ...declared(service) } } }

Origines construites dans resolve-deploy-context.ts (chaque backing Service connaît son name ∈ SERVICE_NAMES et les clés de son loadEnv().secret), threadées via DeployInput → deployContainer → writeServiceEnvFiles (deploy-container.ts:194-215). Le registry_auth_secret est résolu séparément depuis ALL_SECRETS (inchangé).

⚠️ Ordre obligatoire

Retirer le broadcast après avoir câblé la projection par needs ET la validation needs ⊆ backing services déclarés — sinon un service qui a besoin de postgres mais oublie needs=["postgres"] perd DATABASE_URL silencieusement. La validation fait échouer à la config (fail loud), pas au runtime.

04 · Build args par service — un map uniforme

Chaque service build déclare build_args (NOMS). L'infra résout chaque nom contre ALL_VARS et écrit le map dans la cible bake de CE service. Aucune var privilégiée, aucune valeur dans le toml.

fluxpar service build
deploy.yml
ALL_VARS: ${{ toJSON(vars) }} sur le job build-image
▼
resolveBuildArgs (nouveau, domain)
pour chaque service build : build_args ⟶ valeurs depuis ALL_VARS
▼
renderBakeFile
→ target.<svc>.args = { … }
▼
docker buildx bake → ARG → ENV → inline dans dist/ de CE service
fail loudgarde-fous
CI
un build_args déclaré absent de ALL_VARS → throw immédiat dans resolveBuildArgs
▼
Dockerfile
doit déclarer ARG <NAME> ; un arg non déclaré est ignoré par bake (sans erreur)
▼
isolation
les args de front ne touchent pas l'image de api (cibles bake distinctes)

Note d'env-scoping (context7) : ALL_VARS = toJSON(vars) ne voit les Variables de niveau environnement que si le job déclare environment: — ce qui placerait le build derrière le gate prod. Donc : Variables au niveau repo/org (mêmes valeurs dev/prod) → build non gaté. C'est le défaut recommandé.

05 · Le pool [deploy].secrets : point de correctness

On ne peut pas supprimer [deploy].secrets globalement : Cloudflare Pages n'a pas de services (un seul unité déployable, pas de [deploy.services.*]) et s'en sert pour synchroniser l'env vers le projet Pages. La fuite n'existe que sur le target multi-service. Donc on scope la refonte :

TargetDéclaration des secretsPourquoi
hetzner-vps (app/conteneur)par service (services.<n>.secrets + needs). [deploy].secrets dérivé = union, jamais déclaré.multi-service → least privilege requis (c'est le cas de fleurs)
cloudflare-pages (static)[deploy].secrets conservé (déclaration au niveau deploy)pas de services, une seule unité, aucune fuite possible

Implémentation : secrets sort de BaseDeploySection → reste sur CloudflarePagesDeploySection. Pour Hetzner, la validation dérive config.deploy.secrets = union(services[].secrets) — donc resolve-deploy-context.ts:78 (pickSecrets(repoSecrets, config.deploy.secrets)), merged.secret et l'écriture GITHUB_ENV restent inchangés (ils lisent toujours un config.deploy.secrets, juste dérivé). Le fail-loud sur secret GitHub manquant reste dans pickSecrets.

Greenfield (règle repo)

Suppression directe du [deploy].secrets côté VPS, pas de fallback ni de migration. Le nextnode.toml de monitoring est réécrit (secrets → [deploy.services.app].secrets) dans la même PR que le changement de schéma.
