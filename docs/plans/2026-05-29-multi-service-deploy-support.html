Risques

Contract deployContainer change — passe de image: ImageRef à images: Record<service, ImageRef>. Casse migrate.command.ts + cli/deploy/resolve-deploy-context.ts + tests.
High
Refacto type-driven : le compiler force chaque call site à se mettre à jour. Un test e2e existant doit continuer à pass (single-service legacy).
Backward-compat fragile — la rule « absence de [deploy.services] → comportement legacy avec url = project.domain » sans test explicite = régression silencieuse possible sur tous les apps existantes.
High
Test dédié resolve-services-backward-compat.test.ts sur un fixture nextnode.toml minimal (sans [deploy.services]) qui asserte le service synthétisé depuis [deploy.image] avec url = project.domain.
Cold-start sans depends_on entre services — avec le modèle symétrique parallèle, un service qui en requête un autre au boot (ex. front qui SSR-call api) peut taper avant que l'autre soit healthy → 500.
Med
Le champ depends_on?: string[] au niveau service permet d'expliciter l'ordre quand nécessaire. Default = parallèle après backings healthy. Doc explicite dans README.
Healthcheck par service mandatory dès qu'un autre service fait depends_on dessus — sans healthcheck, le rollout bloque indéfiniment.
Med
Default HTTP GET / sur le port interne du service (interval 10s, retries 6) injecté par renderComposeFile si le Dockerfile n'en définit pas.
Bake multi-target temps de build — si les services ont peu de layers communs, build N images en série dans le même bake peut allonger le pipeline vs matrix parallèle.
Low
Cache buildx mutualisé absorbe la plupart des cas. Si gêne réelle observée sur un caller, basculer vers matrix sous flag bake_mode = "parallel" (out of MVP).
