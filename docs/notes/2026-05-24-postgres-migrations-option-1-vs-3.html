Decision Record · Postgres migrations · 2026-05-24

Migration sidecar vs migration dans l'entrypoint app

« Wtf pourquoi un migrate sidecar ? C'est normal toute cette complexité pour une bdd ? »
TL;DR

Pour l'infra NextNode actuelle (single-VPS, single-replica, postgres jamais bind sur l'hôte) : Option 1 (migration dans l'entrypoint app) est largement suffisante. Le sidecar one-shot (Option 3 du backlog P8) ne devient une vraie victoire qu'en multi-replica ou multi-VPS — contexte qu'on n'a pas et qui demande de toute façon une refonte plus large quand il arrive. Le coût d'attendre est nul : ajouter le sidecar plus tard est un ajout local de ~120 LOC, pas un rewrite.

§1 Le besoin réel

Quand on déploie une app avec Drizzle, il faut que le schéma soit migré avant que l'app accepte du trafic. Sinon le premier hit qui touche une table renommée renvoie une 500. La question n'est pas « est-ce qu'on migre » mais « où on exécute pnpm drizzle-kit migrate et comment on bloque le démarrage de l'app jusqu'à ce que ce soit fini ».

Trois familles de solutions existent. Une est exclue d'office : faire tourner les migrations depuis le runner CI (GH Action) en se connectant à Postgres en remote — ça demande d'exposer Postgres sur l'hôte (port 5432 bind) ou de monter un tunnel Tailscale jusqu'au VPS. Or la doctrine NextNode pose une règle : Postgres ne sort jamais du réseau Docker du compose project. Donc reste deux options : entrypoint app, ou sidecar interne au compose.

Option 1 · recommandé

Migration dans l'entrypoint app

L'app, à son démarrage, lance pnpm drizzle-kit migrate avant de booter le serveur. Postgres reste interne, un seul service applicatif dans le compose, zéro nouveau concept dans @nextnode-solutions/infrastructure.

Pour

  • Simplicité radicale : 0 nouveau service compose. postgres + app, point final.
  • Aucun couplage cross-package. @nextnode-solutions/infrastructure reste agnostique du stack de migration. Drizzle aujourd'hui, Prisma demain, raw SQL pour un autre client : 0 ligne à toucher dans le package infra.
  • Une seule image pulled sur le VPS — pas de duplication logique migrate/app.
  • Crash-loop visible et auto-réparant : si migrate plante, l'app crash-loop. docker compose logs app raconte tout. Quand Postgres remonte, l'app retente naturellement.
  • Postgres reste interne via depends_on: { postgres: service_healthy } côté app — pas de port host à ouvrir.
  • ~120 LOC NON écrites dans le package infra (les 4 tâches P8 restantes disparaissent).

Contre

  • Race condition en multi-replica : si demain on lance 2 replicas de l'app, chaque replica essaie de migrer en parallèle au boot. drizzle-kit migrate n'a pas de verrou applicatif natif — deux migrations concurrentes peuvent corrompre l'état.
  • Mélange light de concerns dans l'entrypoint app : démarrer le serveur HTTP et migrer la DB. Documenté et largement adopté (Rails, Phoenix, Django font ça), mais ce n'est pas single-responsibility pur.
  • Migrations replayed à chaque restart : drizzle-kit est idempotent (skip celles déjà appliquées), c'est un no-op ~50ms. Mais c'est un appel DB inutile sur chaque docker compose restart app.

Impact infra actuelle · single-VPS, single-replica

  • Aucun risque de race : 1 seul container app, donc 1 seule migration concurrente possible.
  • Postgres déjà unbind sur l'hôte (D2 du backlog) → satisfait sans rien faire.
  • Tâches Linear INT-592 (committée en working tree, à revert), INT-594, INT-595, INT-593 → toutes annulées.
  • La décision de migration vit désormais côté app (Dockerfile / entrypoint du template d'app), pas dans @nextnode-solutions/infrastructure. Layer infra reste pur orchestrateur générique.
  • Préserve la flexibilité multi-client : chaque app NextNode garde le choix de son outil de migration.

Impact infra future · multi-replica, multi-VPS, scale-out PME/ETI

  • Multi-replica même VPS : ajout d'un verrou. Soit pg_advisory_lock en preflight (~15 LOC dans l'entrypoint), soit switch vers Option 3 (le sidecar one-shot devient le verrou implicite).
  • Multi-VPS : depends_on ne protège pas entre docker compose up sur deux VPS différents. Le verrou est résolu au niveau de l'orchestration externe (Ansible décide qui migre, Terraform pose un lock S3, etc.) — pas dans l'entrypoint, pas non plus avec Option 3.
  • K8s / Nomad : on migre vers un initContainer (k8s) ou lifecycle: prestart (nomad) — exactement le pattern de l'Option 3 mais standardisé. Pas de refactor de l'app : on déplace les 2 lignes de l'entrypoint vers un manifest.
  • Réversibilité : passer à Option 3 plus tard = ajouter buildPostgresMigrateSidecar dans le domaine infra + le wiring. ~120 LOC additives, pas un rewrite. Le coût d'attente est nul.
Option 3 · plan P8 actuel

Sidecar one-shot migrate

Un service migrate dédié dans le compose, image = image app, command = pnpm drizzle-kit migrate, restart: 'no'. L'app attend via depends_on: { migrate: service_completed_successfully }. Doctrine D3 v2 du backlog P8.

Pour

  • Une seule migration par déploiement, quel que soit le nombre de replicas app. Le service migrate est unique par compose project.
  • Séparation propre des concerns : l'entrypoint app ne fait que démarrer le serveur. La migration est explicite dans le compose, auditable via docker compose ps.
  • Logs migrate isolés : docker compose logs migrate retourne uniquement les logs de migration, sans bruit applicatif.
  • Clean fail : si la migration foire, l'app ne démarre pas du tout. Pas de crash-loop bruyant — juste un service migrate qui exit ≠ 0, état non-ambigu.
  • Préfigure le pattern initContainer K8s / Nomad. Mental model identique le jour où on porte.

Contre

  • +1 service dans le compose à chaque deploy, même quand 0 migration à appliquer. Coût du noop drizzle-kit ≈ 200ms — pas un problème de perf, juste du bruit dans compose ps.
  • Couplage infrastructure ↔ Drizzle : la commande ['pnpm', 'drizzle-kit', 'migrate'] vit dans le domaine infra. Si un client utilise Prisma, refactor à prévoir (paramétrer la commande via nextnode.toml).
  • ~120 LOC à écrire + maintenir : 3 fonctions (buildPostgresMigrateSidecar, wiring renderComposeFile, snapshot tests) + 1 démo E2E. 4 tâches Linear restantes en P8.
  • Le bénéfice principal (single-runner) ne sert à rien en single-replica — sur-ingénierie dans le contexte actuel.

Impact infra actuelle · single-VPS, single-replica

  • Coût d'écriture : ~120 LOC + tests + démo E2E. 4 tâches Linear restantes à shipper.
  • Aucun bénéfice concret vs Option 1 dans ce contexte : 0 race possible, 0 multi-replica.
  • Couple le package infrastructure à Drizzle — la 1ère réutilisation par un client non-Drizzle demandera un refactor (paramétrage de la commande).
  • Postgres jamais bind sur l'hôte → satisfait (mais aussi satisfait par Option 1).

Impact infra future · multi-replica, multi-VPS, scale-out

  • Multi-replica même VPS : vraie victoire. migrate tourne 1 fois, les N replicas app attendent. 0 race à gérer.
  • Multi-VPS : faux gain. Chaque VPS lance son propre docker compose up → chaque compose project crée son service migrate. Race entre VPS persiste (à résoudre par orchestration externe, comme avec Option 1).
  • K8s / Nomad : le pattern se traduit 1-to-1 en initContainer / lifecycle: prestart. On a appris les rouages avant le portage.
  • Multi-client NextNode : si un client n'utilise pas Drizzle, le couplage hardcoded devient un coût (refactor pour paramétrer la commande). Anti-pattern « build-or-borrow » : on a réimplémenté ce qu'un initContainer manifest fait nativement, mais à la main et sans portabilité.

§4 Recommandation

Décision · 2026-05-24

Option 1 — migration dans l'entrypoint app

Pour le contexte NextNode actuel (PME/ETI early-stage, single-VPS, single-replica, postgres jamais bind sur l'hôte), l'option 1 satisfait toutes les contraintes sans ajouter de code dans @nextnode-solutions/infrastructure. Le sidecar one-shot serait justifié dans un contexte multi-replica — mais on n'y est pas, et y aller demanderait de toute façon une refonte plus large (load-balancer, sticky sessions, observabilité par replica).

Le coût d'un éventuel switch vers le sidecar plus tard est faible : ajouter buildPostgresMigrateSidecar dans le domaine infra + le wiring dans renderComposeFile. Pas un rewrite, un ajout local — donc il n'y a aucun coût à reporter cette décision.

Re-déclencheurs · quand reconsidérer Option 3

  • Premier client NextNode qui passe en multi-replica (load-balancer en front, N containers app).
  • Migration de l'infra vers Kubernetes ou Nomad (le sidecar devient un initContainer natif).
  • Apparition d'un script pré-migration non-trivial (seed, data migration en plusieurs étapes) qui justifierait un service isolé.
  • Apparition d'un second stack de migration (Drizzle + Prisma sur des clients différents). À ce moment-là, paramétrer la commande dans nextnode.toml + un sidecar paramétré devient justifié.

§5 Concrètement, qu'est-ce qu'on fait maintenant ?

Plan d'action si on retient Option 1

  1. Revert le travail INT-592 : git restore packages/infrastructure/src/domain/services/postgres.ts packages/infrastructure/src/domain/services/postgres.test.ts. Working tree clean après ça.
  2. Annuler les Linear restantes en P8 : INT-592, INT-594, INT-595, INT-593. État canceled, raison « Option 3 retenue par erreur — switch vers Option 1, décision documentée le 2026-05-24 ».
  3. Mettre à jour le plan local : /tmp/claude/go-infra-p8-20260524T132337/plan.md → marquer P8 comme clos.
  4. Côté template d'app NextNode (hors core) : ajouter pnpm drizzle-kit migrate && exec node … dans le Dockerfile / docker-entrypoint.sh. Cette décision vit dans le repo de l'app, pas dans @nextnode-solutions/infrastructure.
  5. Documenter D3 : déposer cette page dans packages/infrastructure/docs/ (ou ajouter une ADR markdown qui pointe dessus) pour que la décision survive à l'oubli et serve de référence le jour des re-déclencheurs.
