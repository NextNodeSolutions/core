Ce qu'il faut retenir du flux

La lane BUILD n'existe que dans le job build-image et n'a aujourd'hui aucune entrée (PR #18 a retiré les args). La lane RUNTIME (job deploy) est intacte. Tout le wiring à décider concerne donc le seul job build-image : comment remplir le map des build args — N variables, toutes au même rang. Le classement se fait par quand la valeur est lue, pas par son nom : PORT lu au démarrage → runtime ; R2_CDN_URL / SITE_URL lus à la config ou inlinés → build. Les variantes ne diffèrent que sur le remplissage de ce map.

Le job build-image aujourd'hui (le point de départ)

Variante A · allow-list build_vars recommandée

toml: 1 champ (noms)renderer: +argsSeules les variables explicitement listées deviennent des build args. Valeurs dans GitHub Variables.

1 · toml — noms seulement (jamais de valeur)

2 · workflow — le job build-image gagne 2 env

@@ env: @@ PIPELINE_CONFIG_FILE: ${{ github.workspace }}/${{ inputs.config_file }} + PIPELINE_ENVIRONMENT: ${{ inputs.environment }} GITHUB_REPOSITORY: ${{ github.repository }} GITHUB_SHA: ${{ github.sha }} + ALL_VARS: ${{ toJSON(vars) }}

Le step « Build and push » ne change pas : les args sont déjà dans le JSON que files: charge.

3 · ce que compute-image-ref rend

4 · contrat Dockerfile (commun à toutes les variantes)

+ Pour
  • Exposition minimale : seul le nécessaire entre dans l'image
  • Auditable : on lit la liste des args dans le toml
  • Symétrique de secrets = [...] — même mental model
  • Valeurs jamais commitées
− Contre
  • 1 champ de schema à ajouter + valider
  • Le dev doit déclarer chaque nom (léger)

Variante B · pass-through de toutes les vars

toml: zérorenderer: +argsToute Variable GitHub devient un build arg. Aucun champ toml.

workflow — identique à A pour l'env

@@ env: @@ PIPELINE_CONFIG_FILE: ${{ github.workspace }}/${{ inputs.config_file }} + PIPELINE_ENVIRONMENT: ${{ inputs.environment }} GITHUB_REPOSITORY: ${{ github.repository }} GITHUB_SHA: ${{ github.sha }} + ALL_VARS: ${{ toJSON(vars) }}

La différence est dans compute-image-ref : au lieu de piocher une allow-list, il émet un arg par clé présente dans ALL_VARS (plus toute valeur calculée par l'infra). Pas de build_vars, pas de toml. Toutes les vars sont traitées à l'identique.

+ Pour
  • Zéro champ toml, zéro maintenance
  • Une nouvelle var → dispo au build sans toucher au repo
− Contre
  • Toutes les vars gravées dans les layers, même inutiles → bruit + surface
  • Implicite : rien n'indique ce qui finit dans l'image
  • Une var mal classée (qui aurait dû être secrète) fuite dans l'image
⚠️ Le risque clé

Le pass-through supprime la barrière qui empêche une valeur sensible mal rangée en vars d'être gravée dans l'image. L'allow-list (A) garde cette barrière.

Variante C · convention par préfixe

toml: zérorenderer: +argsToute Variable préfixée (ex. BUILD_*) devient un build arg — le préfixe EST l'allow-list. Aucune var privilégiée, aucun champ toml.

workflow — mêmes 2 env qu'en A/B

@@ env: @@ PIPELINE_CONFIG_FILE: ${{ github.workspace }}/${{ inputs.config_file }} + PIPELINE_ENVIRONMENT: ${{ inputs.environment }} GITHUB_REPOSITORY: ${{ github.repository }} GITHUB_SHA: ${{ github.sha }} + ALL_VARS: ${{ toJSON(vars) }}

compute-image-ref émet un arg pour chaque clé de ALL_VARS commençant par BUILD_ (préfixe retiré du nom de l'arg). Toutes au même rang :

+ Pour
  • Zéro champ toml, mais scopé (≠ B qui prend tout)
  • Une var de build se reconnaît à son préfixe
  • Barrière préservée : une var sensible non préfixée ne fuite pas dans l'image
− Contre
  • Convention implicite à documenter (le préfixe)
  • Renomme les Variables (préfixe BUILD_)
  • Collision si une var légitime commence par BUILD_ sans être un arg

+ Annexe · un secret nécessaire AU build

Cas rare (ex. token privé d'un registre npm lu pendant pnpm install). Jamais un build arg — ça grave dans les layers. La voie sûre = un secret mount BuildKit : présent pendant le RUN, absent de l'image finale.

workflow + bake target

🔒 Invariant

Un secret au build = --mount=type=secret. Un secret en ARG/build-arg est un bug de sécurité (lisible via docker history + poussé sur GHCR).

! Le piège environment: (à connaître avant de choisir)

Les Variables GitHub existent à deux niveaux. Ça décide où poser R2_CDN_URL et si le build est gaté.

Niveau de la VariableVisible par build-image ?Per-env (dev/prod) ?Effet sur le build
Repo / Orgoui, toujoursnon (même valeur partout)aucun — build non gaté
Environnement (dev/prod)non, sauf si le job déclare environment:ouidéclarer environment: soumet le build aux règles de protection → build gaté derrière l'approbation prod
Conséquence concrète

Aujourd'hui build-image n'a pas de clé environment: (seul deploy en a une, pour le prod gate). Si R2_CDN_URL a la même valeur dev/prod → la poser en Variable repo → visible sans rien gater. Si elle diffère par env → il faut une Variable d'environnement + environment: ${{ inputs.environment }} sur build-image, ce qui place la construction derrière le gate prod (souvent indésirable : on veut builder, puis gater). Pour fleursdaujourdhui, R2_CDN_URL est très probablement identique partout → Variable repo, build non gaté.

🎯 Recommandation pour NextNode

Variante A, valeurs en Variables repo/org (build non gaté) : explicite, auditable, exposition minimale, symétrique du secrets = [...]. Toutes les vars de build y sont au même rang — tu listes les noms, l'infra résout les valeurs (Variable ou calcul). C (préfixe) évite le champ toml si tu préfères une convention BUILD_*. B seulement avec très peu de vars. Orthogonal : l'input set: de bake-action peut surcharger n'importe quel arg par run, sans toucher au reste. Difficulté A : I3 dans @nextnode/core.

À confirmer pour fleursdaujourdhui (repo hors monorepo core) : valeur de R2_CDN_URL identique dev/prod ? sinon le piège environment: s'applique.
