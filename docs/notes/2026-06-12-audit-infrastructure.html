Audit complet du package infrastructure

Cartographie exhaustive du CLI de CI/CD : pipelines, cycle de vie VPS, services backing, secrets, état — avec points faibles, quick wins et préparation du chantier monitoring.

Demande — audit complet de la partie infrastructure, diagramme COMPLET du fonctionnement (toutes les features), weak points, code inachevé, quick wins, améliorations futures, en anticipant le développement du monitoring des apps.

Le package est un CLI de 16 commandes (~17 000 LOC source, ~23 500 LOC tests) consommé exclusivement par 8 workflows GitHub Actions. Il déploie sur deux cibles (Hetzner VPS multi-tenant + Cloudflare Pages), provisionne trois services backing (R2, Postgres, Supabase), et stocke son état dans R2 avec verrouillage ETag. L'architecture en 4 couches strictes (kernel → domain → adapters → cli) est saine et bien testée. Les faiblesses principales : un VPS = point unique de défaillance, aucune métrique machine (pas de node_exporter), aucun alerting, plusieurs chemins de teardown incomplets (buckets R2, stack Supabase, secrets GitHub), et des timeouts/valeurs codés en dur. Les fondations monitoring existent déjà (Vector → VictoriaLogs, relabel rules, postgres-exporter) mais ne couvrent que les logs et Postgres-sous-Supabase.

01Topologie générale

Tout part de nextnode.toml : les workflows GitHub Actions invoquent le CLI (node src/index.ts <cmd>), qui pilote Cloudflare, Hetzner et Tailscale. L'état vit dans R2, jamais en local.

Le routage des commandes (src/index.ts:31-54) distingue trois familles : plan (config brute, même non déployable), deploy (exige une config déployable app/static) et standalone (sans config : prod-gate, publish, recover, restore, build-golden-image). Un projet type = "package" passe par publish-package.yml et saute silencieusement les commandes deploy.

02Pipelines CI/CD — toutes les séquences

Cinq pipelines distincts consomment le CLI. Chacun est détaillé ci-dessous ; le lecteur compare, il ne lit pas en séquence.

Pipeline le plus riche (.github/workflows/deploy.yml, concurrence sérialisée par (config_file, environment)). Le job plan émet quality_matrix, has_postgres, has_domain, image_source, upstream_image_refs vers GITHUB_OUTPUT ; les jobs suivants se conditionnent dessus.

Le modèle d'environnement est binaire : production → domaine nu, development → préfixe dev. (DNS non proxifié, TTL 300). Il n'existe pas d'environnement préview par PR. Le prod-gate (src/domain/pipeline/prod-gate.ts) refuse un deploy prod si le pipeline dev du même SHA n'a pas conclu en succès.

deploy-static.yml — léger, sans concurrence. Un projet Pages par environnement (name et name-dev), chacun avec son historique et ses domaines.

publish-package.yml — pour les type = "package" (logger, standards, email-manager, brand-assets). L'infrastructure elle-même passe par cette route mais n'est jamais publiée sur npm.

Deux workflows manuels (workflow_dispatch) avec chaîne de confirmation obligatoire, plus une commande de rattrapage d'orphelins.

build-golden-image.yml — l'image de base des VPS, reconstruite quand le fingerprint du cloud-init change ou que le snapshot dépasse 30 jours.

03Anatomie d'un VPS et rollout

Un VPS est multi-tenant : plusieurs projets cohabitent derrière un seul Caddy. Le rollout en deux phases garantit que Postgres est sain et migré avant de basculer l'app.

Points structurants relevés dans le code :

  • État à trois phases (adapters/hetzner/state/types.ts) : created → provisioned (IP tailnet + empreinte SSH) → converged. Toute écriture passe par un verrou optimiste ETag ; un conflit lève EtagMismatchError sans retry automatique.
  • SSH TOFU : l'empreinte de clé hôte est capturée à la première connexion (comparaison timing-safe) et figée dans l'état R2. Aucun mécanisme de rotation.
  • Convergence idempotente (cli/hetzner/converge.ts:31-73) : lit la config Caddy/Vector existante, ne pousse et ne redémarre que si diff. Vector est sauté si NN_VL_URL est injoignable au provision — sans alerte, les logs restent non expédiés jusqu'à la convergence suivante.
  • Rollout deux phases (adapters/hetzner/deploy-container.ts:101-137) : phase 1 monte Postgres et les sidecars à l'état healthy, la migration tourne entre les deux, phase 2 bascule l'app. Invariant : le bloc Postgres du compose doit être octet-identique entre phases.
  • Caddy multi-tenant (adapters/hetzner/rollout.ts:208-248) : la reconfiguration extrait les upstreams existants, retire ceux du projet courant, fusionne, et recharge sans coupure. Aucune validation (caddy validate) avant le reload.
  • Ports hôte : plage fixe [8080, 8200) = 121 ports par VPS, allocation idempotente persistée dans l'état.

04Services backing (R2 · Postgres · Supabase)

Le registre SERVICE_DEFINITIONS (complétude vérifiée à la compilation) expose deux opérations par service : provision() au provision, loadEnv() au deploy. Les env produits fusionnent sans collision (sinon throw) : target → services → secrets user.

  • Buckets : <projet>-<env>-<alias>, déclarés dans [[services.r2.buckets]] ; un alias backups est ajouté implicitement si Supabase est déclaré.
  • Token par projet/env : nextnode-r2-<projet>-<env>, scoped aux buckets déclarés ; credentials S3 dérivés (accessKeyId = token.id, secret = SHA256(token.value) — la valeur brute n'est jamais stockée). Rotation auto-guérissante : les tokens homonymes périmés sont révoqués à chaque provision.
  • Propagation : sondage SigV4 5 × 3 s — au-delà, le provision échoue (pas de backoff).
  • CDN : cdn = true attache <alias>.cdn.<domaine> (CNAME auto-créé par Cloudflare via zoneId, attente ssl = active).
  • État : services/r2/<projet>/<env>.json ; vérifié au deploy — credentials périmés = échec sec, sans self-heal (asymétrie avec le provision qui, lui, ré-rotationne).
  • Mode embedded : sidecar postgres:18 épinglé, rôle/DB dérivés du nom de projet, volume nommé local. DATABASE_URL en canal secret, hostname interne postgres (jamais de port hôte).
  • Backups : sidecar postgres-s3-backup:18, dump quotidien vers nn-backups-<projet>, rétention GFS 7 jours / 4 semaines / 3 mois.
  • Migrations : conteneur éphémère sur le VPS (pnpm drizzle-kit migrate par défaut, surchargeable), snapshot pré-migration ; checkCommand tourne côté runner dans la quality matrix.
  • Restore : infra restore --project --at <iso> --yes (gate destructive explicite). Aucune validation post-restore.
  • Mode external : passthrough du secret DATABASE_URL, zéro provisioning.
  • Stack auto-hébergée de 6 conteneurs épinglés (db supabase/postgres:17.6, gotrue, realtime, storage, kong, studio) ; kong routé publiquement par Caddy, studio derrière basic-auth.
  • Secrets : PG_EXPORTER_PASSWORD, POSTGRES_PASSWORD, JWT_SECRET auto-générés et poussés en env-secrets GitHub (idempotents, non rotatifs) ; DASHBOARD_PASSWORD doit être posé manuellement par l'opérateur (échec sec sinon).
  • JWT : ANON_KEY/SERVICE_ROLE_KEY dérivés déterministiquement (HS256, iat: 0) — pas de churn côté clients.
  • Exporter : postgres-exporter:v0.18 sur :9187, lié à l'interface Tailscale, rôle SQL pg_monitor en lecture seule.
  • Config : [services.supabase] est une table vide — pur interrupteur, aucun knob. Le teardown de la stack n'est pas câblé.

05Modèle de secrets — trois portes

Les valeurs ne vivent jamais dans nextnode.toml : le dev déclare des NOMS, résolus contre les snapshots GitHub ALL_SECRETS/ALL_VARS gelés au début du job.

Contrat à connaître Un secret généré au provision n'apparaît dans ALL_SECRETS qu'au run suivant (GitHub gèle les secrets au démarrage du job) : le flux nominal est provision → re-déclencher le deploy. Même contrat pour les credentials R2 poussés en org-secrets.

06Monitoring : existant et trous, avant le chantier apps

Les fondations côté collecte existent ; tout le reste (métriques machine, alerting, sondes) est à construire. C'est la section à lire avant de démarrer le développement du monitoring.

✅ Déjà en place

  • Logs : Vector (golden image) expédie docker + journald vers VictoriaLogs en NDJSON avec champs nn_project/nn_client_id (domain/hetzner/vector-config.ts).
  • Filtrage scrape : tag Tailscale client-vps + whitelist fermée de 7 labels (domain/monitoring/client-vps-relabel.ts) — le budget cardinalité est déjà gouverné.
  • postgres-exporter :9187 lié au tailnet, rôle pg_monitor read-only, rotation du mot de passe via la commande dédiée rotate-pg-exporter-password.
  • App monitoring : déployée en interne (nn-internals, cx33, tailnet only) via ce même pipeline — le monitoring se déploie avec l'outil qu'il surveille.
  • Healthchecks compose : contrat GET /healthz pour les images NextNode, gating service_healthy.

⚠️ Manquant

  • Aucune métrique machine : pas de node_exporter ni cAdvisor dans la golden image — CPU/RAM/disque/conteneurs invisibles.
  • Caddy non scrapé : l'endpoint de métriques admin n'est ni activé ni exposé au tailnet.
  • postgres-exporter limité à Supabase : un Postgres embedded seul n'a aucun exporter.
  • Aucun alerting : échecs de rotation de tokens, de renouvellement de certs, de backups, Vector sauté — tout finit en simple log.
  • Aucune sonde d'uptime externe sur les URLs déployées ; pas de vérification de propagation DNS avant ACME.
  • Aucun événement de deploy publié (annotations) : impossible de corréler un incident à un déploiement.
  • Label db_role réservé mais jamais câblé (propagation services.supabase.role, P6-08 annulée).
  • Logger : le CLI logge sur stdout uniquement ; le transport HTTP de @nextnode-solutions/logger n'est pas utilisé.
Recommandation d'architecture Le chantier monitoring peut s'appuyer à 100 % sur les conventions existantes : ajouter node_exporter + cAdvisor à la golden image (un rebuild suffit, le fingerprint déclenche la reconstruction), activer l'admin Caddy sur le tailnet, généraliser postgres-exporter, puis faire scraper le tout par la VM nn-internals via le tag client-vps déjà filtré. L'alerting (vmalert + alertmanager) se déploie comme stack multi-services du projet monitoring — exactement le cas d'usage visé par la spec multi-service-deploy.md.

07Points faibles

Constats vérifiés dans le code, classés par gravité. Aucun TODO/FIXME ne traîne dans les sources — les faiblesses sont structurelles, pas des oublis marqués.

VPS unique = SPOF haut
Aucun failover ni multi-VPS : la panne d'un serveur emporte tous les projets qu'il héberge (dont nn-internals, qui porte le monitoring lui-même).
Court terme : alerting externe sur l'uptime. Moyen terme : affinité multi-VPS dans la config.
Angle mort observabilité haut
Sans métriques machine ni alerting, un disque plein, une fuite mémoire ou un échec de backup ne se détectent qu'à la panne.
node_exporter/cAdvisor dans la golden image + vmalert — voir section 06.
Credentials R2 en org-secrets moyen
ensure-setup.ts:50-75 pousse les credentials R2 avec --visibility all : tout repo de l'org peut les lire.
Réduire au scope repo/environnement (l'adapter env-secrets existe déjà pour Supabase).
SSH TOFU sans rotation moyen
L'empreinte hôte est figée à la première connexion ; une clé compromise n'a aucun chemin de rotation. Atténué par le transport tailnet.
Commande de re-pin opérateur + doc runbook.

Inventaire détaillé

  • fiabilité Propagation token R2 : 5 × 3 s fixes (cli/r2/token-lifecycle.ts:11-13) — un pic de latence Cloudflare fait échouer tout le provision.
  • fiabilité docker compose pull sans retry : registre flaky = deploy échoué immédiatement.
  • fiabilité Healthcheck Postgres 60 s codé en dur (deploy-container.ts:43) : un initdb lent sur SSD chargé échoue sans option de réglage.
  • fiabilité Pas de caddy validate avant reload : une config malformée laisse l'ancienne en place silencieusement.
  • fiabilité Pas d'attente de propagation DNS avant l'ACME : certs en échec à la première émission, retry manuel.
  • cohérence EtagMismatchError sans retry ni indication du gagnant de la course — l'opérateur doit relancer à l'aveugle.
  • cohérence Provisioning services en Promise.all : un échec au milieu laisse buckets/domaines partiellement créés sans reprise.
  • teardown Buckets R2 jamais supprimés (aucun deleteR2Bucket) ; domaines Pages obsolètes seulement loggés, jamais détachés ; stack Supabase et secrets GitHub générés survivent au teardown.
  • teardown recover ne nettoie ni DNS ni routes Caddy (le serveur est déjà détruit) — résidus manuels.
  • sécurité Authkey Tailscale : shred uniquement si tailscale up réussit — un échec laisse le fichier (0600, TTL 10 min, risque borné).
  • sécurité Login registre Docker partagé dans ~/.docker/config.json du VPS : pas d'isolation par service.
  • dette extractRootDomain = heuristique « deux derniers segments » : casse sur .co.uk et autres TLD composés.
  • dette Builder golden image figé cx23/nbg1 ; plage de ports [8080, 8200) ; tous les timeouts en constantes non configurables.
  • dette Résumé de deploy émis seulement en succès ; validation du token registre et des IMAGE_REFS trop tardive (au runtime du deploy plutôt qu'au plan).
  • dette Restore sans validation post-restauration (aucun check que la DB répond après pg_restore --clean).

08Code et features inachevés

  • Spec docs/specs/multi-service-deploy.md marquée « Draft » alors que l'essentiel (services multiples, routing par service, secrets par service, needs) est implémenté et testé. Le statut et les sections « planned files » sont périmés — à réconcilier avant le chantier monitoring qui s'appuie dessus.
  • Commentaire périmé dans config/types.ts:163-165 : needs est annoté « Reserved for the multi-service wiring landing in M2 » alors que la provenance secretOrigins est câblée de bout en bout.
  • [services.supabase] stub vide : interrupteur sans aucun knob ; la propagation role (P6-08) a été annulée, laissant le label db_role réservé inutilisé dans la whitelist monitoring.
  • Teardown Supabase absent : seuls le détachement des domaines CDN et le wipe opt-in des backups existent ; les 6 conteneurs et les secrets GitHub générés restent.
  • Aucun workflow planifié (cron) : pas de convergence périodique, pas de recover automatique, pas de rebuild golden image à 30 jours (la limite d'âge n'est vérifiée qu'à l'occasion d'un provision), pas de vérification de fraîcheur des backups.
  • Pas d'environnements préview par PR : le modèle s'arrête à dev/prod.
  • Hetzner Block Volumes non intégrés : volumes nommés sur SSD local uniquement (choix documenté, mais sans escape hatch implémenté).

09Quick wins

Faible effort, gain immédiat — ordonnés par rapport gain/effort.

  • → node_exporter + cAdvisor dans la golden image — un ajout au cloud-init, le fingerprint déclenche le rebuild ; débloque le chantier monitoring. ~½ j
  • → caddy validate avant chaque reload — une commande SSH de plus dans reconcileCaddy. ~1 h
  • → Retry + backoff exponentiel sur docker compose pull et la propagation des tokens R2. ~½ j
  • → Workflows cron : recover hebdomadaire en dry-run (rapport d'orphelins), rebuild golden image mensuel, sonde de fraîcheur des backups. ~½ j
  • → Credentials R2 en env-secrets au lieu d'org-wide (EnvSecretsAdapter déjà disponible). ~2 h
  • → Généraliser postgres-exporter au mode embedded sans Supabase (le module domain existe déjà). ~½ j
  • → Timeout healthcheck configurable par service dans nextnode.toml. ~2 h
  • → Résumé de deploy aussi en échec + validation des tokens registre/IMAGE_REFS remontée au plan. ~2 h
  • → Mettre à jour la spec multi-service (statut, fichiers livrés) et le commentaire needs de config/types.ts. ~1 h
  • → Détacher les domaines Pages obsolètes derrière un flag explicite (aujourd'hui simple warn). ~2 h
