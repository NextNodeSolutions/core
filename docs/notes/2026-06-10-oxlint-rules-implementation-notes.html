01Harnais de test — choix structurants

Pas de mock : chaque suite exécute le vrai binaire oxlint sur des fixtures générées, et lit les diagnostics JSON.

manifest TSbad / edge / good
tmpdirfixtures écrites
oxlint --format json1 run / suite
assertions vitest
un seul process oxlint par suite — pas un par cas
  • Config passée par -c src/oxlint/base.js directement. Un wrapper defineConfig posé dans /tmp ne peut pas résoudre le module oxlint (résolution Node relative au fichier) — découvert à la première tentative.
  • Fixtures en template strings dans le manifest, jamais en fichiers à plat dans src/ : sinon le lint du package explose sur ses propres fixtures volontairement fausses.
  • Interprétation du goal TDD : « cas fonctionnel » = le code fautif déclenche la règle avec la bonne sévérité ; « edge » = variante piégeuse avec attente explicite (fire ou clean) ; « non-fonctionnel » = good-case par règle (zéro faux positif) + suite dédiée : chargement config sans erreur, zéro règle inconnue, module exemplaire 100 % conforme aux skills → zéro diagnostic, DSL vitest toléré, budget perf < 30 s.

03Tradeoffs et décisions hors-spec

Décision promise/prefer-await-to-then passe en warn au lieu d'error : la règle flagge aussi task().catch(report), l'idiome sanctionné par le skill js pour le fire-and-forget intentionnel. Le ban dur reste porté par typescript/no-floating-promises (type-aware, error).
  • no-with non testable : un statement with est une erreur de parse en module strict — couvert par la catégorie correctness par défaut, sans test dédié.
  • react/react-in-jsx-scope désactivé : warnait sur tout JSX sans import React, obsolète avec le JSX runtime moderne. Découvert en fixture .tsx.
  • no-empty-function avec allow: ['arrowFunctions'] : le noop () => {} reste légal ; les fonctions nommées vides restent interdites.
  • max-nested-callbacks off dans les tests : describe > it > expect(() =>) EST le DSL vitest — 20 erreurs structurelles dans logger avant le fix. Couvert par un test non-fonctionnel dédié.
  • Niveaux warn assumés (jugement humain requis) : prefer-destructuring, no-await-in-loop (séquentiel parfois voulu), no-non-null-assertion (le ! prouvable est toléré par le skill), no-generic-names, no-use-effect, no-underscore-dangle (allow __dirname/__filename).
  • import/no-default-export avec exemptions framework : fichiers config, app/** Next.js (page/layout/…), pages/**, middleware.ts, stories. Dans le package standards lui-même, override src/** : chaque module shippé EST une config consommée en default export.
  • Plugin restructuré : plugins/no-type-assertion.js → plugins/rules/*.js (une règle par fichier, SRP) + agrégateur plugins/nextnode.js — deux plugins ne peuvent pas partager le nom nextnode.
  • declare enum toléré par no-enum : une déclaration ambiante décrit du code tiers, pas le nôtre.
  • Em dash auto-référence : fixtures et plugin écrits avec l'échappement — ; 43 em dash littéraux retirés de mes propres commentaires au premier self-lint (le linter m'a linté).
  • Dogfooding du harnais : le self-lint a forcé la réécriture des deux as du harnais en type guards (isExecFailure, isOxlintOutput) + renommages (booleanDefault → hasBooleanDefault, result → destructuring). La config s'applique ses propres règles : 0 erreur, 0 warning.
  • peerDependencies : oxlint relevé à >=1.62.0 (no-array-sort, preserve-caught-error absents de 1.58) ; oxlint-tsgolint >=0.23.0 ajouté en peer optionnelle — les règles type-aware ne s'activent qu'avec oxlint --type-aware.

05Extension SRP / React (2e itération, sur demande)

« SOLID/SRP + split surtout sur React, c'est pas possible avec oxlint ? » — le jugement non, les proxys syntaxiques oui.

  • Natifs ajoutés : react/no-multi-comp (warn — un composant par fichier ; flag aussi les sous-composants privés = pression à l'extraction, documenté en edge), react/jsx-max-depth: 8 (un arbre JSX profond = composant qui fait trop), max-params: 4 (au-delà → options object), import/max-dependencies: 20 (warn — proxy god-module, ARCH 1).
  • Custom ajoutés : nextnode/max-props (warn — >5 props destructurées sur une fonction PascalCase ; les fonctions camelCase sont exemptes car le gros options object y est le pattern RECOMMANDÉ), nextnode/component-filename-match (error — fichier PascalCase nommé d'après son unique export composant, index.tsx exempt), nextnode/no-grab-bag-files (error — utils/helpers/misc/common.ts bannis, date-utils.ts toléré : le domaine est nommé).
  • Comportement découvert : jsx-max-depth compte la profondeur sous la racine (racine = 0) ; et les visitors jsPlugin peuvent être invoqués deux fois sur Program:exit → garde hasReported dans component-filename-match pour dédupliquer.
  • Toujours non mécanisable : « ce composant mélange deux responsabilités », « ces helpers sont non-reliés », single level of abstraction — le linter mesure des seuils, pas des concepts.

08Étude des skills v4 + slim v5 (2026-06-10)

Avant de porter les skills de style (coding, javascript, typescript, react, architecture) de la branche v4 vers v5, audit d'exactitude / efficience / efficacité. Résultat : ~88 KB de skills réduits à ~58 KB, le mécanisé remplacé par un préambule « Enforced by the linter », le jugement conservé intégralement.

Erreurs factuelles corrigées

  • structuredClone (javascript) : le skill affirmait « throws on functions at the top level but drops them inside objects ». Faux — vérifié sous Node : DataCloneError sur une fonction à n'importe quelle profondeur. Ce qui est perdu silencieusement : le prototype des instances de classe (méthodes). Texte corrigé.
  • Exemples ??= / ||= (javascript) : les exemples mutaient config.port (un paramètre) — en conflit direct avec no-param-reassign {props:true} désormais mécanisé. Réécrits sur de l'état local.
  • Règle em-dash (coding) : la ligne du quick-ref affichait un U+002D en prétendant montrer un U+2014 (le fichier avait été dé-em-dashé lui-même). Devenue inutile — règle mécanisée (nextnode/no-em-dash), ligne supprimée.
  • Préambule react : référençait le hook react-ts-gate, absent de v5 (seul pnpm-guard.sh subsiste). Réécrit : l'enforcement vient d'oxlint.
  • forwardRef (react RULE 7) : « deprecated » était légèrement en avance — React 19 rend forwardRef obsolète (ref = prop), la dépréciation formelle est annoncée. Nuancé, guidance inchangée.

Conflit tranché : value == null

Le skill javascript tolérait l'idiome value == null ; le config mécanisé le flagge (vérifié : eslint(eqeqeq) sans option). oxlint supporte ["error","always",{"null":"ignore"}] (vérifié : 0 diagnostic). Décision : strict conservé — l'exception est retirée du skill, cohérent avec le zéro-tolérance ===. Revenir en arrière = une ligne d'option dans base.js.

Seuils réconciliés (skill aspirationnel vs lint plafond)

  • Fonctions : viser ~20 lignes (skill), plafond dur 50 (lint). Composants inclus — l'ancien « ~150 lignes par composant » du skill react était incohérent avec le plafond, supprimé.
  • JSX : viser ~3-4 niveaux (skill), plafond dur 8 (lint, compté sous la racine).
  • Fichiers : 250 lignes (lint), aligné avec le « ~200-250 » du skill.

Structure du slim

Chaque skill ouvre sur un bloc « Enforced by the linter - do not re-derive, just comply » listant ce qu'oxlint couvre, puis ne garde que le jugement : single level of abstraction, naming domaine, DRY/AHA, SOLID, tables « instead of any/as », unions discriminées, allSettled vs all, Map/Set, doctrine useEffect (effects.md = manuel de fix du warn nextnode/no-use-effect), composition React, Jotai. jotai.md, effects.md, composition.md, patterns.md, architecture.md, ops-discipline.md portés quasi inchangés (tout est jugement). Le skill workflow architecture est porté avec ses références aux skills absents de v5 (interview, project-docs) neutralisées. nextnode-standards/oxlint.md réécrit avec la table réelle des 217 règles résolues (pin >= 1.62.0, plugin nextnode 10 règles, section type-aware).

Références pendantes restantes

Les skills v4 test, vitest, interview, project-docs, learn, next, astro, turborepo n'existent pas en v5 — les renvois ont été retirés ou adoucis ; si ces skills sont portés plus tard, les renvois peuvent être rétablis.
