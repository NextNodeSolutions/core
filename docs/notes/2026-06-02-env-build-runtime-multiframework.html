Architecture · variables d'environnement · build vs runtime

Comment l'env atteint (ou pas) le build :
le mécanisme, et toutes les voies

Pourquoi un .env ne suffit pas en CI, où vit chaque valeur (jamais dans nextnode.toml), et comment alimenter build + runtime pour tous les frameworks (Astro, Next.js, SolidJS, Hono…).

Question « Si tu passes pas les env dans Dockerfile / docker-compose, ce putain d'Astro les voit pas même s'il y a un .env ? — et JAMAIS d'env dans le nextnode.toml. Check TOUTES les possibilités. »

01 · Le problème, en une phrase

Une variable ne vit pas à un seul moment. Certaines sont gelées au build (inlinées dans le bundle livré au navigateur), d'autres lues au runtime (à chaque requête, côté serveur). En CI/Docker, le .env n'existe pas (il est gitignoré + exclu par .dockerignore) : Astro au build ne voit que ce que Docker injecte via ARG/ENV. PR #18 a retiré ce pont (les build.args de l'ancien compose) sans le remplacer.

02 · Le mécanisme : pourquoi Astro ne voit rien

Le point qui coince. Il y a deux portes totalement distinctes, et le .env n'en franchit aucune dans Docker.

localTa machine
astro dev / astro build sur ton poste
  • Vite lit .env via loadEnv
  • import.meta.env + process.env peuplés
  • ✅ tout marche → ça crée l'illusion que « le .env suffit »
Le .env n'existe QUE là. C'est une porte locale.
CI · builddocker build
contexte hermétique — pas ta machine
  • .dockerignore exclut **/.env → jamais dans le contexte
  • loadEnv ne trouve rien
  • process.env = uniquement ce que ARG/ENV injectent
❌ sans build args → requireEnv("SITE_URL") throw. C'est ton cas.
🔑 Les deux portes Docker (le .env n'en est pas une)

Porte BUILD = ARG dans le Dockerfile, alimenté par build.args (ancien compose) ou args de la bake. Porte RUNTIME = env_file / environment → process.env à chaque requête. L'ancienne infra avait la porte build (docker-compose.yml → args) ; PR #18 l'a murée. La porte runtime, elle, est intacte — c'est pourquoi les secrets astro:env/server marchent au runtime sans rien faire.

Confirmé dans le repo : .dockerignore (racine) contient **/.env et **/.env.local ; le Dockerfile monitoring n'a aucun ARG (il n'inline rien au build) ; BuildServiceConfig n'a pas de champ args.

03 · Les 2 phases : qui lit quoi, quand

phase 1BUILDdocker build

Ce qui est lu ici est inliné / gelé dans dist/ :

  • Variables client du bundle JS (NEXT_PUBLIC_*, VITE_*, PUBLIC_*, astro:env context:'client')
  • Valeurs lues dans la config du framework (Astro site → canonicals + sitemap, image.domains)
⚠️ Source : ARG/ENV uniquement. Les secrets ne doivent jamais arriver ici.
phase 2RUNTIMEdocker run

Ce qui est lu ici reste variable par environnement, même image :

  • Secrets serveur — getSecret(), process.env serveur
  • Config publique serveur (SSR / loader / route)
  • Valeurs publiques rendues dans le HTML au runtime
✅ Déjà câblé : .env.<service> via env_file (secrets + SITE_URL + URLs + PORT).
— même image · BUILD gèle ▸ RUNTIME injecte —

09 · Le fix infra corrigé · zéro valeur dans le toml

Faire porter la correction par la plateforme. Les valeurs vivent dans GitHub (Secrets pour le sensible, Variables pour le public) — exactement comme secrets = [...] qui ne liste que des noms (valeurs ← ALL_SECRETS → pickSecrets).

1 · Le toml ne liste que des NOMS (comme secrets)

Décision à valider (c'est toi qui tranches)

build_vars = [...] est une liste de noms, zéro valeur — même forme que secrets. Alternative sans aucun toml : convention « tout vars est forwardé en build arg » → zéro champ ajouté, mais moins explicite. Troisième voie : seul SITE_URL (dérivé) est forwardé d'office, et tout autre besoin passe par l'échappatoire runtime du framework → aucun nouveau câblage. Je recommande la liste de noms (explicite, auditable, symétrique de secrets).

2 · Le workflow forwarde les Variables (symétrique d'ALL_SECRETS)

@@ env: @@ PIPELINE_CONFIG_FILE: ${{ github.workspace }}/${{ inputs.config_file }} + PIPELINE_ENVIRONMENT: ${{ inputs.environment }} + ALL_VARS: ${{ toJSON(vars) }} GITHUB_REPOSITORY: ${{ github.repository }} GITHUB_SHA: ${{ github.sha }}

3 · renderBakeFile écrit les args (dérivés ∪ vars nommées)

@@ interface BakeTarget @@ readonly target?: string + readonly args?: Readonly<Record<string, string>> readonly tags: ReadonlyArray<string> @@ buildBakeTarget @@ dockerfile: service.dockerfile ?? defaultDockerfile(input.packageDir), + ...(Object.keys(input.buildArgs).length ? { args: input.buildArgs } : {}), tags: [formatImageRef(ref)],

input.buildArgs = { SITE_URL dérivé de domain } ∪ { les build_vars piochées dans ALL_VARS }. Aucun secret, jamais.

4 · Le Dockerfile expose les ARG avant le build (contrat app)

Pourquoi c'est le bon endroit

Les valeurs restent dans GitHub (Secrets / Variables), jamais dans le repo. Le toml ne porte que des noms — même contrat que secrets. Difficulté : I3 — champ build_vars + lecture ALL_VARS + rendu des args + 2 lignes de workflow + tests. Tout futur site containerisé en bénéficie sans rien écrire côté app.
