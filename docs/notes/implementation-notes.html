Implementation notes — PRD Monitoring VPS

Démarré le 2026-06-13. Décisions hors-spec, changements et tradeoffs pris pendant l'implémentation de docs/plans/2026-06-13-prd-monitoring-vps.html.

Décisions d'architecture (hors spec ou précisées)

vmagent en network_mode: host — la PRD ne précise pas le réseau de vmagent. Depuis le réseau compose, scraper les exporters des VPS clients via le tailnet fonctionne (MASQUERADE docker), mais scraper le node_exporter/cAdvisor de nn-internals lui-même est bloqué par UFW (le trafic conteneur→hôte arrive sur docker0, interface non autorisée). En host networking, vmagent voit nativement tailscale0 (scrape tailnet), localhost:9100/9101 (self), 127.0.0.1:8428 (remote_write VM) et le host-port de l'app Astro (endpoint SD). Aucune règle UFW supplémentaire, aucune exposition réseau nouvelle.
Endpoint SD joint via le host-port de l'app — vmagent (host net) appelle http://127.0.0.1:<hostPort app>/api/sd/targets (le port que Caddy utilise déjà), pas le vhost HTTPS. Évite une dépendance TLS/DNS interne pour la découverte.
VL/VM exposés sur des ports localhost fixes — 127.0.0.1:9428 (VictoriaLogs) et 127.0.0.1:8428 (VictoriaMetrics), hors plage apps [8080,8200). Caddy route les vhosts logs./metrics. vers ces ports. Pas d'allocation dynamique : ports bien connus, déterministes, un seul stack observability par VPS (fail loud sinon).
Choix du tag Tailscale — la PRD demande tag:client-vps pour les VPS clients et tag:monitoring pour nn-internals, sans dire comment décider. Règle : un projet qui déclare [services.observability] → son VPS reçoit tag:monitoring ; sinon tag:client-vps. Reproductible, pas de cas spécial nn-internals.
Secrets Alertmanager rendus inline au deploy — Alertmanager ne fait pas d'interpolation d'env dans son YAML (contrairement à ce que la PRD esquisse avec "${RESEND_API_KEY}"). Le fichier alertmanager.yml est rendu en TS au deploy avec les valeurs injectées, poussé par SFTP à côté de compose.yaml — même posture de sécurité que les .env.* déjà poussés.
