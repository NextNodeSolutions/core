Implementation notes — PRD Monitoring VPS

Démarré le 2026-06-13. Décisions hors-spec, changements et tradeoffs pris pendant l'implémentation de docs/plans/2026-06-13-prd-monitoring-vps.html.

Décisions d'architecture (hors spec ou précisées)

vmagent en network_mode: host — la PRD ne précise pas le réseau de vmagent. Depuis le réseau compose, scraper les exporters des VPS clients via le tailnet fonctionne (MASQUERADE docker), mais scraper le node_exporter/cAdvisor de nn-internals lui-même est bloqué par UFW (le trafic conteneur→hôte arrive sur docker0, interface non autorisée). En host networking, vmagent voit nativement tailscale0 (scrape tailnet), localhost:9100/9101 (self), 127.0.0.1:8428 (remote_write VM) et le host-port de l'app Astro (endpoint SD). Aucune règle UFW supplémentaire, aucune exposition réseau nouvelle.
Endpoint SD joint via le host-port de l'app — vmagent (host net) appelle http://127.0.0.1:<hostPort app>/api/sd/targets (le port que Caddy utilise déjà), pas le vhost HTTPS. Évite une dépendance TLS/DNS interne pour la découverte.
VL/VM exposés sur des ports localhost fixes — 127.0.0.1:9428 (VictoriaLogs) et 127.0.0.1:8428 (VictoriaMetrics), hors plage apps [8080,8200). Caddy route les vhosts logs./metrics. vers ces ports. Pas d'allocation dynamique : ports bien connus, déterministes, un seul stack observability par VPS (fail loud sinon).
Choix du tag Tailscale — la PRD demande tag:client-vps pour les VPS clients et tag:monitoring pour nn-internals, sans dire comment décider. Règle : un projet qui déclare [services.observability] → son VPS reçoit tag:monitoring ; sinon tag:client-vps. Reproductible, pas de cas spécial nn-internals.
Secrets Alertmanager rendus inline au deploy — Alertmanager ne fait pas d'interpolation d'env dans son YAML (contrairement à ce que la PRD esquisse avec "${RESEND_API_KEY}"). Le fichier alertmanager.yml est rendu en TS au deploy avec les valeurs injectées, poussé par SFTP à côté de compose.yaml — même posture de sécurité que les .env.* déjà poussés.
Deux instances vmalert (metrics + vlogs) — vmalert ne lie qu'une datasource par process. vmalert évalue les règles PromQL contre VictoriaMetrics ; vmalert-vlogs évalue les groupes type: vlogs (LogsQL) contre VictoriaLogs et remote-write ses recording rules (nn:log_lines_15m, nn:http_*) dans VictoriaMetrics. Toutes les alertes vivent donc côté metrics ; le vlogs ne fait que des recording rules. Cela contourne le risque PRD §11 (compat vmalert↔VictoriaLogs sur l'état d'alerte) : les LogsQL ne servent qu'à produire des séries jointes ensuite en PromQL.
Watchdog sévérité none + receiver devnull — si HEALTHCHECKS_PING_URL n'est pas configuré, le Watchdog (qui fire en permanence) ne doit jamais tomber sur l'email. Route severity = "none" → devnull (sink), et si le DMS est configuré, route alertname = "Watchdog" → deadmansswitch (heartbeat ~4 min).
Métrique de fraîcheur des backups en PULL, pas PUSH — la PRD esquissait un curl push depuis le conteneur postgres-backup. À la place, l'app control-plane liste le bucket nn-backups-<project> (SigV4 GET, lecture seule) et expose nn_backup_last_success_timestamp_seconds{project} sur /api/metrics/backups, scrapé par un job vmagent backups (5 min, honor_labels). Avantage : zéro modification du conteneur de backup, zéro credential d'écriture nouveau, et ça marche pour le mode embedded comme Supabase.
postgres-exporter embedded : rôle dédié, mot de passe = POSTGRES_PASSWORD — le sidecar exporter du Postgres embedded monte le même bootstrap SQL que Supabase (rôle postgres_exporter pg_monitor, PAS superuser) et bind ${TS_IP}:9187. Le mot de passe du rôle réutilise POSTGRES_PASSWORD : même .env, mêmes conteneurs, un secret généré séparé n'ajouterait que de la rotation sans réduire la surface. Pas de custom-queries (pg_stat_statements nécessite shared_preload_libraries, absent de l'image postgres:18 vanilla — présent sur supabase/postgres) : le metric set built-in (pg_up, connexions, tailles) couvre les règles P6. Si Supabase ET postgres embedded sont déclarés, Supabase possède le nom postgres-exporter et le port 9187 (un seul exporter par port VPS).
URLs VictoriaMetrics/VictoriaLogs en dur dans l'app (P5) — l'app monitoring et le stack observability partagent le même projet compose (le stack est injecté dans le compose de l'app via [services.observability]). L'app atteint http://victoriametrics:8428 / http://victorialogs:9428 par nom de service compose : contrat fixe du stack, pas une config. Jamais de host-port, jamais l'IP publique. En dev local le stack est injoignable → les panneaux dégradent en bannière d'erreur (loadPageState). Requêtes bornées par timeout 5 s.
Sémantique nn_project (niveau VPS) — vue VPS par slug, vue projet par container_name — Vector est configuré à la convergence au niveau VPS : NN_PROJECT = nom du VPS (input.vpsName), donc toutes les lignes d'un VPS portent nn_project=<vpsName>, pas le nom du projet déployé. La désambiguïsation par projet se fait via container_name = <project>-<env>-<service>-N (compose -p <project>-<env>). Résolu après audit : la vue VPS interroge logs+Caddy par nn_project:<slug> (= vpsName, montre tout le VPS) ; la vue projet isole les logs conteneurs par préfixe regex container_name:~"^<project>-". Aucun remap VRL fragile dans Vector : la correction est entièrement côté requête. Les stats Caddy sont par-VPS (Caddy est un service hôte unique qui reverse-proxy tous les vhosts) — la vue projet ne montre donc que les logs conteneurs, pas de panneau HTTP par-projet (les lignes par domaine sont sur la vue VPS).

Tradeoffs

cAdvisor en host-publish ${TS_IP}:9101 vs UFW — comme postgres-exporter, la publication Docker contourne UFW (iptables DOCKER chain). La seule protection est donc l'adresse de bind = IP tailnet. node_exporter (binaire hôte, :9100 sur toutes interfaces) est lui protégé par double couche UFW (tailscale0 only) + firewall Hetzner Cloud (80/443/22). Acceptable : c'est exactement le pattern postgres-exporter déjà en prod.
SD émet 9187 pour tout VPS client — l'état R2 n'enregistre pas quels VPS ont un postgres-exporter. Le job postgres reçoit donc une cible 9187 pour chaque VPS client ; un VPS sans exporter montre up=0 sur ce job, mais aucune alerte ne s'en sert (PgDown surveille pg_up, métrique émise seulement par un exporter répondant). Évite de maintenir une liste.

Changements par rapport à la spec

Alertes machine scopées job="node" (PRD : job="client-vps") — la découverte émet un job vmagent par exporter (node, cadvisor, postgres) plutôt qu'un seul client-vps, pour qu'une cible postgres-exporter morte ne fasse pas croire le VPS down. VpsDown = up{job="node"} == 0 : seul node_exporter atteste la liveness machine.
labelkeep relabel élargi — la whitelist fermée d'origine (^(__name__|client_id|...)$) aurait supprimé __address__/job/instance au scrape, tuant toute collecte. Corrigé en ^(__.*|job|instance|<whitelist>)$ : __address__ est consommé pour émettre le scrape, job/instance sont l'identité sur laquelle chaque alerte s'appuie.

Revue adversariale (workflow multi-agents)

Audit cross-fichiers — 10 problèmes confirmés, corrigés — un workflow de 5 reviewers (contrats, sémantique-logs, sécurité, PromQL/LogsQL, reproductibilité) + vérification adversariale (22 agents) a trouvé un cluster de bugs log-pipeline maintenant corrigés :
  • CRITIQUE — sink Vector n'envoyait pas _msg_field/_time_field → logs vides côté VictoriaLogs. Corrigé (vector-toml.ts).
  • CRITIQUE — filtre Caddy "logger":"http.log.access" ne matchait jamais (valeur réelle http.log.access.logN, et corps dans message pas _msg). Corrigé : unpack_json puis filter logger:~"^http\.log\.access".
  • CRITIQUE — alertes HTTP lisaient $labels.host mais les recording rules émettent request.host → annotation vide. Corrigé via label_replace.
  • CRITIQUE/HIGH — dashboards interrogeaient par slug projet alors que nn_project=vpsName → zéro ligne sur hôte partagé. Corrigé (vue VPS par nn_project, vue projet par container_name).
  • HIGH — VectorSilent joignait sur project (jamais satisfiable : logs host-keyed, metrics project-keyed). Corrigé : join sur vps_name.
  • HIGH/MEDIUM — labels relabel environment/region/container_name sans source SD → réservés null (contrat honnête), retirés des by d'alerte.
7 faux positifs réfutés (ex. ordering metric_relabel cAdvisor correct, BackupStale aligné, volumes teardown non-orphelins). La sécurité a passé l'audit : aucune exposition publique nouvelle (firewall Hetzner 80/443/22, UFW tailscale0-only, exporters bind ${TS_IP}, vhosts internal), pas de fuite de secrets.

À savoir / actions opérateur

2 tests préexistants rouges (hors scope) — create-hetzner-target.test.ts et create-cloudflare-pages-target.test.ts « throws when CLOUDFLARE_API_TOKEN is missing » échouent localement car la variable CLOUDFLARE_API_TOKEN est exportée dans le shell du dev (le test ne l'isole pas). Rouges avant tout ce travail (baseline), sans rapport avec le monitoring, verts en CI. Bug d'isolation de test à corriger séparément.
ACL Tailscale (action manuelle) — ajouter dans l'ACL du tailnet : tagOwners pour tag:client-vps et tag:monitoring (owner = le client OAuth d'infra), et un grant tag:monitoring → tag:client-vps:9100,9101,9187. Sans ça, le mint d'authkey taggué échoue et vmagent ne pourra pas scraper.
Variables d'org GitHub — définir NN_VL_URL=https://logs.monitoring.nextnode.fr et NN_CLIENT_ID=nextnode après le déploiement P1, puis re-provisionner la flotte.
Compte healthchecks.io — créer le check (période ~5 min, grâce ~10 min) et pousser HEALTHCHECKS_PING_URL en secret GitHub du projet monitoring. RESEND_API_KEY doit aussi exister. Le domaine alerts@nextnode.fr doit être vérifié dans Resend (from des emails d'alerte).

Validation stylot + ordre de déploiement

Config stylot — compatible, deploy-ready — ~/Development/tools/stylot/nextnode.toml parse avec le nouveau schéma : type=app, postgres mode=embedded, pas de [services.observability] (correct : c'est un client, pas l'hôte monitoring) → tag client-vps. Le compose généré inclut bien : web (healthcheck /healthz, depends_on postgres healthy), postgres:18 + mount 00-pg-monitor.sql, postgres-backup (nn-backups-stylot), postgres-exporter bindé ${TAILSCALE_IP}:9187 connecté en postgres_exporter@postgres/stylot. node_exporter/cAdvisor viennent de la golden image. Tout le monitoring de stylot est automatique au provisioning.
Recommandation — VPS dédié pour stylot — sans vps= dans [deploy], stylot atterrit sur le VPS prod partagé nn-prod (défaut). Le monitoring fonctionne (logs par container_name, métriques par projet, probes par domaine), mais la page VPS est /vps/nn-prod et nn_project=nn-prod. Pour matcher la PRD (/vps/stylot, nn_project=stylot) et isoler proprement le premier client de prod, ajouter vps = "stylot" sous [deploy] de stylot (repo stylot, hors core). Non bloquant.
Ordre de déploiement (greenfield)
  1. Merge ce travail dans main de core (les workflows lisent l'infra depuis le monorepo).
  2. Préparer l'ACL Tailscale (tagOwners client-vps+monitoring, grant monitoring→client-vps:9100,9101,9187), le compte healthchecks.io, les secrets RESEND_API_KEY+HEALTHCHECKS_PING_URL sur le projet monitoring, le domaine Resend.
  3. Déployer le projet monitoring (nn-internals) : provision recrée le VPS depuis la nouvelle golden image (node_exporter+cAdvisor+tag:monitoring), le compose injecte le stack observability (VL/VM/vmagent/vmalert×2/AM/blackbox), Caddy front logs./metrics.
  4. Définir les variables d'org GitHub NN_VL_URL=https://logs.monitoring.nextnode.fr et NN_CLIENT_ID=nextnode.
  5. Provisionner/déployer stylot (après P2) : naît de la nouvelle golden image, Vector ship les logs (convergence écrit vector.env avec NN_VL_URL), SD le découvre par tag, les 18 règles le couvrent sans déclaration.
  6. Valider les critères §11 par injection de panne sur l'env dev de stylot avant prod.
