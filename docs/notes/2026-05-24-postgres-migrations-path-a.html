Postgres reste interne, l'image app n'est pas touchée, la commande migrate est pluggable ([services.postgres].migrate_command, défaut node scripts/migrate.js).

Phase Linear P8 ré-ouverte, 6 nouvelles issues [P8-07..12] (INT-596 → INT-601). Les anciennes [P8-03..06] restent canceled.

§1 Ce que le premier audit a raté

Le record v1 a comparé « entrypoint app » vs « migrate sidecar » et recommandé entrypoint. Il a omis ce qui existait déjà dans packages/infrastructure :

  • cli/deploy/migrate.command.ts — commande CLI migrate, registered dans index.ts. Lit DATABASE_URL, applique les migrations via le runtime migrator drizzle-orm.
  • adapters/postgres/drizzle-runner.ts — wrapper pg.Client + drizzle-orm/migrator.
  • [services.postgres].migrationsFolder dans la config + validation.
  • Concurrency group dans deploy.yml avec le commentaire « protects DB migrations and traffic swap from concurrent runs » — le design assumait un step migrate en CI.

Mais le step migrate n'est pas câblé dans le workflow. Et l'hypothèse sous-jacente (le runner CI peut atteindre postgres:5432) est fausse en embedded — ce hostname ne résout que dans le réseau docker du compose project, pas depuis le runner. La commande est orpheline et ne fonctionnerait pas telle quelle.

Path A finit cette orchestration en déplaçant l'exécution du migrate sur le VPS (où le réseau docker résout) au lieu du runner.

§2 Topologie Path A

Phase 1 — provision + db up
runner CI → ssh → VPS
docker compose up -d postgres postgres-backupwait until healthy
Phase 2 — backup snapshot + migrate
docker compose exec postgres-backup sh backup.shlog R2 dump key in GH summary
docker run --rm --network <silo>_default \ --env-file <envDir>/.env <image> \ sh -c "$migrate_command"
postgres:5432 résout via docker DNS — postgres jamais bind sur l'hôte
Phase 3 — app rotation
docker compose up -d --remove-orphans appcaddy upstream swap
deploy.yml → provision → migrate (this) → deploy (app rotation)

§4 Pluggable command

Le couplage Drizzle reste optionnel via un champ de config :

Défaut node scripts/migrate.js = pattern NextNode. Le template d'app ship un scripts/migrate.js qui utilise le runtime migrator drizzle-orm/node-postgres/migrator (~10 LOC, pas besoin de drizzle-kit en runtime dep).

Un client Prisma override migrate_command = "pnpm prisma migrate deploy" et check_command = "pnpm prisma migrate diff --exit-code". Un client raw SQL met migrate_command = "sh scripts/apply-sql.sh". @nextnode-solutions/infrastructure ne sait rien du stack — il sait juste comment SSH-exécuter une commande dans un container éphémère joint au réseau docker.

§6 Travail côté app NextNode (template)

Path A demande un seul ajout côté template d'app (hors core) :

  • apps/<app>/scripts/migrate.js — le snippet ~10 LOC ci-dessus.
  • drizzle-orm et pg en runtime deps (pas devDeps) — l'image prod doit les contenir.
  • S'assurer que le drizzle/ folder est COPY dans l'image Docker au build.

Aucune modif du Dockerfile ENTRYPOINT / CMD : l'app continue de démarrer son serveur HTTP comme avant. Le migrate vit en parallèle dans un container éphémère piloté par la pipeline.
